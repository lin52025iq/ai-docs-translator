下表展示了各项文档功能在转换流程三个阶段中的表现：

1. **导入**：将 DOCX 内容转换为 Tiptap JSON。
2. **编辑器**：在浏览器中渲染这些 JSON。每种节点和标记类型都需要对应的 Tiptap 扩展才能正确显示。
3. **导出**：将编辑器中的内容转换回 DOCX 文件。

某项功能可能在一个阶段受支持，而在另一个阶段不受支持。例如，制表符会在导入时保留并在编辑器中渲染，但导出扩展目前还不会将其写回 DOCX。

导入和导出各有两种集成方式：[编辑器扩展](/conversion/import/docx/editor-extension)和 [REST API](/conversion/import/docx/rest-api)。对于大多数功能，两种方式的结果相同。对于存在差异的功能（脚注、页眉/页脚、导出自定义），相应的安装页面会说明具体情况。

<Callout variant="info" title="编辑器列以 ConvertKit 为前提">
  下表中的编辑器列假定采用推荐配置：将 [ConvertKit](/conversion/import/docx/convertkit) 安装为编辑器的扩展套件。ConvertKit 包含基础功能的超集（相当于 StarterKit 的节点，以及针对 Paragraph、Heading、Image 和表格组件的 DOCX 专用覆盖）。如果不使用 ConvertKit，段落间距和缩进、图像裁剪以及表格单元格格式会被提取到 JSON 中，但会被编辑器的 schema 丢弃。编辑器支持依赖其他组件（例如 Pages 或自定义扩展）时，表格行中会注明依赖项。
</Callout>

## 其他格式

这些表格专门介绍 DOCX 转换流程，因为所有其他导出格式都以 DOCX 为基础。[PDF](/conversion/export/pdf/editor-extension)、[ODT](/conversion/export/odt/editor-extension)、[EPUB](/conversion/export/epub/editor-extension) 和 [DOC](/conversion/export/doc/editor-extension) 都会先生成 DOCX 文件，再通过云服务将其转换为目标格式。通常，DOCX 导出支持的功能也会保留到其他格式中，但各格式可能有自身的限制。详情请参阅相应格式的页面。

[Markdown](/conversion/export/markdown/editor-extension) 使用完全独立的转换流程，支持的功能也有所不同。相关说明请参阅其单独页面。

## 文本和段落样式

导入服务会从 DOCX 源文件中提取段落级样式属性，例如间距、缩进和行高。ConvertKit 的自定义 Paragraph 和 Heading 会自动渲染这些样式。若要应用文档命名样式目录中的排版样式（Heading 1、Normal、Quote 等），请使用实验性的 [CSS 注入](/conversion/import/docx/css-injection)功能，该功能会将样式目录提取为作用域 CSS 规则。

| 功能 | 导入 | 编辑器 | 导出 |
| --- | --- | --- | --- |
| [文本对齐](/conversion/content-types/text-and-formatting/text-alignment) | ✓ | ✓ | ✓ |
| [行距](/conversion/content-types/text-and-formatting/paragraphs) | ✓ | ✓ | ✓*** |
| [段落间距](/conversion/content-types/text-and-formatting/paragraphs) | ✓ | ✓ | ✓ |
| [缩进](/conversion/content-types/text-and-formatting/paragraphs) | ✓ | ✓ | ✓ |
| [与下段同页 / 段中不分页](/conversion/content-types/text-and-formatting/paragraphs) | ✓ | ✓ | ✓ |
| [字间距](/conversion/content-types/text-and-formatting/font-family-size) | ✓ | ✕* | ✕ |
| [段落边框](/conversion/content-types/text-and-formatting/paragraphs) | ✕ | ✕ | ✕ |
| [Word 样式](/conversion/content-types/structures-and-media/word-styles) | ~ | ~** | ~ |

**\*** 字间距会被提取为 `textStyle.letterSpacing`，但没有内置扩展负责渲染。要渲染导入的字间距，请[扩展 TextStyle](/conversion/getting-started/guides/styling-converted-content#extending-extensions-for-unsupported-attributes)。<br />
**\**** 默认不会应用 Word 命名样式的排版。使用 [CSS 注入](/conversion/import/docx/css-injection)将其提取为作用域 CSS。<br />
**\**** 导出时会保留行距。比例值（无单位倍数，例如 `1.5`，或百分比，例如 `150%`）会写为相对行距，并随字号缩放；带绝对单位的固定值（`24px`、`18pt`、`1cm`）会写为精确行高。`em` 和 `rem` 等相对字体单位则采用文档默认值。

| 功能 | 导入 | 编辑器 | 导出 |
| --- | --- | --- | --- |

**\*** 在 `preserve` 模式下，插入和删除会作为建议保留并在转换过程中往返传递。`accept` 和 `reject` 则会在导入时应用或丢弃这些修订，因此不会有任何内容以建议的形式导入。编辑器渲染需要使用[修订扩展](/tracked-changes/getting-started/overview)。目前仍无法保留某些类型的修订，包括导入时的段落拆分修订、格式更改和移动，以及导出时的格式修订和图像上的建议。这些情况下，内容会保留，但更改记录不会保留。请参阅[导入时的修订](/conversion/import/docx/tracked-changes)和[导出时的修订](/conversion/export/docx/tracked-changes)。

## 不支持的功能

以下功能在导入时不会转换，或仅能有限转换。

| 功能 | 状态 |
| --- | --- |
| 目录 | 导入为 `tableOfContents` 节点（包含标题和标题范围）。要在编辑器中渲染，需要使用[自定义扩展](/editor/extensions/custom-extensions/extend-existing)。现有的[目录扩展](/editor/extensions/functionality/table-of-contents)是用于构建侧边栏导航的无界面工具，并非文档块渲染器。不支持导出。 |
| 文本框 | 不会转换。不会提取文本框中的内容。 |
| 形状、SmartArt、WordArt | 不会转换。导入时不会提取这些元素。 |
| 字段代码（DATE、AUTHOR、MERGEFIELD） | 缓存的显示值会以纯文本形式保留（例如，显示“April 10, 2026”的 DATE 字段会作为文本“April 10, 2026”导入）。字段代码本身不会转换，因此该值会变成静态文本，不再更新。 |
| 页码字段代码（PAGE、NUMPAGES） | 启用 `placeholders` 后，会转换为规范文本标记（`PAGE` 对应 `{page}`，`NUMPAGES` 对应 `{numpages}`；使用 Pages 扩展时默认启用，通过 REST API 的 `placeholders={}` 表单字段选择启用）。Pages 扩展可原生渲染 `{page}`；通过 `Pages.configure({ placeholders: { total: 'numpages' } })` 映射 `{numpages}`，即可实时渲染。设置 `placeholders: false`（或在 REST API 中省略该选项）时，缓存的显示值会以纯文本形式导入。 |
| 文档元数据（作者、标题、关键字） | 不会转换。元数据不会包含在 JSON 输出中。 |
| 表单字段和内容控件 | 部分转换。行内和块级结构化文档标签（SDT）会保留其内容，但控件元数据会被丢弃。复选框内容控件是例外。启用任务列表导入后，以复选框开头的列表项会作为任务项导入，并保留其勾选状态；任务项则会导出为复选框内容控件。请参阅[任务列表](/conversion/content-types/text-and-formatting/task-lists)。 |
| 隐藏文本 | 标记为隐藏的文本运行（`w:vanish`）不会包含在导入结果中。 |
| 从右向左的文本方向 | 导入时不会解析 DOCX `<w:bidi>`（段落方向）和 `<w:rtl>`（文本运行方向），导出时也不会写入这些属性。使用阿拉伯语、希伯来语、波斯语、乌尔都语及其他 RTL 语言编写的文档，会按编辑器的 CSS 方向渲染（默认为 LTR）。目前可在编辑器根节点设置 `dir="rtl"`，或在应用层检测语言来处理。详情请参阅[文本对齐](/conversion/content-types/text-and-formatting/text-alignment)。 |
