修订跟踪扩展的高级行为和集成模式。

## 建议分组

用户连续输入，或连续删除多个字符时，这些编辑会合并为一条建议，而不是每个字符都创建一条建议。符合以下条件时会进行分组：

1. 新编辑与现有建议**相邻**（紧挨其前或其后）
2. 现有建议由**同一用户**创建
3. 现有建议的**类型相同**（都是插入或都是删除）

符合以上全部条件的连续编辑会合并为一条建议。

## 删除合并

用户删除的内容与现有删除建议重叠或相邻时，标记会自动合并，以避免出现嵌套或重叠的删除。合并后的建议使用范围内**最早**的现有删除标记的元数据（ID、用户、时间戳）。

这样可以确保：

- 文档中不会出现嵌套的删除标记
- 相关删除内容会在视觉上归为一组
- 保留最初删除内容的作者

## 混合内容处理

删除或替换的内容同时包含原始文本和先前建议插入的内容时：

- **建议插入内容**（带有 `add` 标记的文本）会立即从文档中移除
- **原始内容**（不带 `add` 标记的文本）会标记为一条 `delete` 建议

这种行为符合用户预期：如果删除的文本只是建议内容（尚未接受），它会直接消失。要移除文档中的原始内容，则必须明确接受该更改。

## 块拆分

扩展使用 `splitKind` 区分两种块拆分：

| 拆分类型 | 发生时机 | 接受 | 拒绝 |
| ------------ | --------------------------------------- | ------------------- | ----------------------- |
| `insertion` | 在块末尾按 Enter | 保留新块 | 移除新块 |
| `structural` | 在现有内容中间按 Enter | 保留两个块 | 再次合并两个块 |

两种类型的 `suggestion.type` 均为 `'split'`。建议面板会在标签中使用受影响的 `nodeType`，例如插入拆分显示为 `new paragraph`，结构拆分显示为 `split heading`。

可在[修订跟踪 Playground](/tracked-changes/examples/simple)中试用这些情况。

### 在末尾拆分属于插入拆分

在段落末尾按 Enter 时，扩展会创建一个新段落，并附带一条 `split` 建议：

```html
<p>First paragraph.</p>
<p data-suggestion data-suggestion-type="blockSplit">Second paragraph.</p>
```

`findSuggestions()` 返回的建议如下：

```ts
{
  type: 'split',
  splitKind: 'insertion',
  nodeType: 'paragraph',
  text: 'Second paragraph.',
  fullText: 'Second paragraph.',
}
```

拆分后输入的文本会保留在同一条插入拆分建议中。建议文本会随新块内容变化。如果你在该块末尾再次按 Enter，第二次拆分会有自己的建议和 ID。

在标题或列表项末尾拆分时也遵循相同规则。对于列表项，新建的 `<li>` 是插入的块。拆分标记会出现在前一个段落末尾，也就是前一个列表项内部。

### 在中间拆分属于结构拆分

在现有内容中按 Enter 时，扩展会跟踪新边界，但不会将第二个块视为新插入的内容。例如，在 `Hello` 和 `World` 之间拆分 `<p>HelloWorld</p>` 会创建一条结构拆分建议：

```html
<p>Hello</p>
<p data-suggestion data-suggestion-type="blockSplit">World</p>
```

该建议的 `splitKind` 为 `'structural'`，`nodeType` 为 `'paragraph'`。它的 `text` 和 `fullText` 包含第二个块中的文本；在此示例中即为 `"World"`。

拆分标题时，`nodeType` 为 `'heading'`，标签类似 `split heading`。在列表项中间拆分时，会保留列表项的替换行为，而不会创建结构拆分 `split` 建议。

### 分别接受或拒绝拆分

接受任一种拆分都会保留两个块并清除建议。拒绝插入拆分会移除新块；拒绝结构拆分会将两个块重新合并。

连续发生的末尾拆分彼此独立。接受或拒绝其中一项不会影响其他拆分。扩展不会将所有连续的末尾拆分合并成一条建议。

拆分标记会呈现在拆分前的块末尾。请参阅 [`blockSplitMarker`](/tracked-changes/getting-started/install#blocksplitmarker)，了解如何配置或移除它。

### `split` 与 `blockSplit`

查询 API 返回 `suggestion.type: 'split'`。节点属性和 `data-suggestion-type` DOM 属性使用 `'blockSplit'`。使用 `findSuggestions()` 时，请按 `'split'` 筛选和判断。只有在通过 CSS 定位渲染后的节点时才使用 `'blockSplit'`。映射关系请参阅 [SuggestionNodeType](/tracked-changes/api-reference/types#suggestionnodetype)。

## 嵌套和堆叠的建议

当一位用户在另一位用户尚未处理的建议**内部**编辑时，该编辑会成为一条独立建议，叠加在原建议之上，并归属于正在编辑的用户，而不会修改或丢弃原建议。这样，多位审阅者就能针对同一段内容提出更改，而不会互相覆盖。

嵌套适用于行内添加、删除和替换。同一作者的编辑方式不变：如果**同一位**用户继续在自己的建议中输入，内容仍会合并为一条建议（参见[建议分组](#suggestion-grouping)）。只有**不同**作者之间才会发生嵌套。

建议堆叠时，外层建议的 `text` 和 `fullText` 字段会有所不同：`text` 是该作者单独贡献的文本，而 `fullText` 则包含嵌套建议在其上插入的文本。详情和示例请参阅 [`text` 与 `fullText`](/tracked-changes/api-reference/types#text-vs-fulltext)。

### 接受和拒绝规则

| 操作 | 结果 |
| ------------------------------ | ------------------------------------------------------------------------------------------------- |
| 接受**内层**建议 | 应用内层建议；**外层**建议保持不变。 |
| 拒绝**内层**建议 | 丢弃内层建议；**外层**建议保持不变。 |
| 接受**外层**建议 | 应用外层建议；其中的**嵌套建议仍然保留**，并作为独立的待处理建议。 |
| 拒绝**外层**建议 | 丢弃外层建议**及其嵌套编辑**，因为这些编辑所依附的内容也会被移除。 |

<Callout title="仅限行内" variant="info">
  仅支持行内建议的嵌套。块级嵌套建议（例如跨越整个块的嵌套建议）不在支持范围内。
</Callout>

## 标记跟踪

修订跟踪还可以将现有文本上的标记级编辑作为 `markChange` 建议进行跟踪。这包括 `bold` 和 `italic` 等简单格式标记，也包括带有属性的标记，例如 `link` 或 `highlight`。

标记跟踪的行为如下：

- 在现有文本上添加或移除标记会创建一条 `markChange` 建议
- 应用于新插入内容的格式会保留在插入建议中，不会另行创建标记建议
- 标记更改建议会保存发生更改的标记名称和属性，因此接受或拒绝时可以正确还原或移除带属性的标记

### 标记跟踪的工作方式

对于现有文本，跟踪的标记更改会记录提议的实际标记变更：

- 添加标记会创建一条操作为 `added` 的 `markChange` 建议
- 移除标记会创建一条操作为 `removed` 的 `markChange` 建议

例如，用户将 `bold` 应用于某个词时，建议会记录添加了 `bold`。用户从已设置格式的文本中移除 `bold` 时，建议会记录移除了 `bold`。

带属性的标记处理方式相同，但属性也属于跟踪更改的一部分。这对 `link` 等标记很重要，因为具体属性决定了更改的是哪一种标记：

```js
// Suggest adding a specific link
editor.commands.addTrackedMark({
  from: 7,
  to: 12,
  markName: 'link',
  markAttrs: {
    href: 'https://tiptap.dev',
    target: '_blank',
  },
})
```

在此示例中，建议会同时保存标记名称（`link`）和标记属性。接受或拒绝该建议时，就可以保留、还原或移除准确的链接标记，而不会将所有链接视为相同。

如果用户对同一段文本应用某个标记后又撤销了同一标记更改，跟踪到的标记更改可以相互抵消，而不会留下多余的建议。这有助于在审阅过程中保持嵌套和重叠标记建议的稳定性。

默认情况下，修订跟踪会忽略 `suggestion` 标记本身以及行内评论/线程标记，以免这些内部标记递归地产生修订建议。你也可以选择不跟踪其他标记：

```js
TrackedChanges.configure({
  ignoredTrackingMarks: ['highlight'],
})
```

如果应用中存在不应出现在修订跟踪中的装饰性标记或集成专用标记，请使用此选项。

## 节点属性跟踪

更新现有节点的属性时，会创建一条 `attributeChange` 建议，而不是替换该节点。这适用于图片等原子节点，以及带有自定义属性的非原子节点。

建议处于待处理状态时，文档中会包含提议的属性值。建议通过 `attributeChanges` 暴露原值和提议值，便于审阅界面说明更改：

```ts
{
  type: 'attributeChange',
  nodeType: 'image',
  attributeChanges: [
    {
      attributeName: 'src',
      oldValue: 'https://example.com/old.png',
      newValue: 'https://example.com/new.png',
    },
  ],
}
```

接受建议会保留提议的值；拒绝建议会还原每个 `oldValue`。如果同一作者在审阅前再次更改属性，建议会保留最初的 `oldValue` 并更新 `newValue`。将属性改回原值后，该属性会从待处理建议中移除。如果这是最后一个发生更改的属性，扩展会取消这条 `attributeChange` 建议。

使用 `[data-suggestion-type="attributeChange"]` 为受影响的节点设置样式。DOM 和 API 详情请参阅[样式设置](/tracked-changes/api-reference/styling)和 [SuggestionAttributeChange](/tracked-changes/api-reference/types#suggestionattributechange)。

## 节点类型更改

通过 [`nodeTypeChangeTypes: ['paragraph', 'heading']`](/tracked-changes/getting-started/install#nodetypechangetypes) 启用此功能后，可将段落转换为标题，并以一条 `attributeChange` 建议表示。源类型和目标类型都必须配置。支持的转换会将一种文本块转换为另一种，同时不更改其内容或节点标记；列表、原子节点、包裹和解除包裹均不支持。

文档会保留一个可见块，并将其显示为提议的类型。可通过现有建议 API 查询：

```ts
import { findSuggestions } from '@tiptap-pro/extension-tracked-changes'

const typeChanges = findSuggestions(editor).filter((suggestion) => suggestion.nodeTypeChange)
// A paragraph converted to a heading exposes:
// type: 'attributeChange'
// nodeType: 'heading'
// nodeTypeChange: { oldValue: 'paragraph', newValue: 'heading' }
```

接受建议会保留提议的类型和属性。拒绝建议会还原原始类型和属性，同时保留当前内容以及可独立审阅的文本和标记建议。使用现有的接受、拒绝、范围、用户和批量审阅命令。通过建议事件或会更改文档的编辑器事务刷新查询。

作者可以使用相同 ID 修改待处理的提议。恢复为完整的原始类型和属性后，提议会被取消。其他作者必须先审阅该提议，才能更改块的类型或属性，但仍可编辑其中的文本和行内标记。

请将类型转换与内容编辑分开提交：同时包含两者的事务会被整体阻止。Markdown 输入规则仍采用替换行为，因为它们也会移除触发文本。会导致原始类型无法还原的编辑（包括无法明确判定的合并）会被阻止。如果导入的内容导致无法还原，拒绝操作会返回 `false`，且不会更改文档；请解决内容冲突或接受提议的类型。批量拒绝被阻止时，文档同样不会更改。即使事务被阻止，普通编辑器命令也可能报告成功，因此显示成功提示前请检查最终文档。

拆分已提出类型更改的块时，两个片段都会保留类型提议，并创建独立的拆分建议。之后，如果类型或属性编辑导致其中一个片段发生差异，就会创建单独的格式建议。拒绝拆分前，请先审阅存在差异的格式。

JSON 会在 `attrs.suggestionNodeTypeChange` 中保留原始类型和属性。HTML 会在 `data-suggestion-node-type-change` 中保留这些信息；请在自定义渲染器中保留此属性，并在节点视图中使用 [`getSuggestionHTMLAttributes(node)`](/tracked-changes/api-reference/utilities#getsuggestionhtmlattributes)。撤销、重做和重新加载都会保留该提议。粘贴副本时会保留可见类型，但不会复制提议的身份信息。打开已保存提议的客户端必须支持节点类型更改。

[拆分视图](/compare/guides/split-view)会在前置面板中显示原始类型，在后置面板中显示提议类型。[DOCX 修订导出](/conversion/export/docx/tracked-changes)要求先接受或拒绝待处理的节点类型提议。

## 表格支持

扩展会跟踪表格中的结构性更改，包括行、单元格和列操作。

**单元格选区删除** — 用户通过 `CellSelection` 删除单元格（即选中多个单元格并按 Delete）时，每个选中的单元格都会提升为节点级删除建议，而不是立即移除。选区中的所有单元格共用同一个 `suggestionId`，因此在建议列表中会显示为一项分组更改。

**删除列** — 删除一列会生成一条跨越该列所有单元格的分组建议，而不是每个单元格各生成一条建议。

**接受和拒绝** — 接受或拒绝表格建议时，会正确处理底层表格节点结构，避免在操作涉及列节点时出错。

若要启用表格跟踪，请在修订跟踪扩展旁加入表格扩展：

```js
import { Table } from '@tiptap/extension-table'
import { TableRow } from '@tiptap/extension-table-row'
import { TableCell } from '@tiptap/extension-table-cell'
import { TableHeader } from '@tiptap/extension-table-header'
import { TrackedChanges } from '@tiptap-pro/extension-tracked-changes'

const editor = new Editor({
  extensions: [
    Table.configure({ resizable: true }),
    TableRow,
    TableCell,
    TableHeader,
    TrackedChanges.configure({ enabled: true, userId: 'user-123' }),
  ],
})
```

无需额外配置 — 两个扩展启用后，表格更改会自动跟踪。

## 原子节点跟踪

扩展会自动跟踪图片、水平线和其他非文本内容等原子节点的更改。这些节点不能带有标记，因此扩展会改用节点属性（`suggestionId`、`suggestionType`、`suggestionUserId`、`suggestionCreatedAt`、`suggestionUserMetadata`）。这些节点的属性更新会作为 `attributeChange` 建议跟踪；其他更改会出现在相同的建议查询中，并且可以像其他建议一样接受或拒绝。

## 协作兼容性

此扩展专为基于 Yjs 的协作场景设计，并会自动忽略：

- 来自 Yjs 的**远程同步事务**（`y-sync$` 元数据）
- **历史记录事务**（撤销/重做由 ProseMirror 原生处理）
- **带有 `addToHistory: false` 的事务**（通常为远程更改）

这意味着只有本地用户编辑会被跟踪为建议。

使用 Tiptap Collaboration（Y.js 文档）时，请将 `nodeTypeChangeTypes` 保持为默认值 `[]`：类型转换仍会使用替换建议。将这类转换记录为单条 `attributeChange` 建议的可选功能仅适用于本地编辑器；在使用 Tiptap Collaboration（Y.js 文档）时配置非空列表会导致初始化失败。如果协作文档中已包含通过此设置创建的提议，那么在兼容的客户端移除这些提议之前，本地文档编辑和审阅都会被阻止。远程同步仍会继续。

## 评论集成

修订跟踪扩展可与[评论](/editor/extensions/functionality/comments)扩展集成，从而支持同时处理建议和评论线程的审阅工作流。该集成基于两个扩展公开的事件系统构建。

两个扩展都启用时，评论线程会通过线程元数据自动关联到建议，从而实现双向同步：

- **解决**关联到建议的评论线程会自动**接受**该建议
- **删除**关联到建议的评论线程会自动**拒绝**该建议
- **接受**建议会自动**解决**关联的评论线程
- **拒绝**建议会自动**删除**关联的评论线程

建议内容发生变化时（例如，用户在受跟踪的插入内容中继续输入），关联线程的元数据也会更新，以保持同步。

这意味着用户既可以通过建议界面，也可以通过评论面板审阅更改 — 两者始终保持一致。

## 代码块兼容性

默认情况下，Tiptap 代码块不允许使用标记，因此无法在代码内容中应用建议标记。扩展提供了一个辅助函数来解决此问题：

```js
import { CodeBlock } from '@tiptap/extension-code-block'
import {
  TrackedChanges,
  withSuggestionMarkOnCodeBlock,
} from '@tiptap-pro/extension-tracked-changes'
import StarterKit from '@tiptap/starter-kit'

const TrackableCodeBlock = withSuggestionMarkOnCodeBlock(CodeBlock)

const editor = new Editor({
  extensions: [
    StarterKit.configure({
      codeBlock: false, // Disable the default code block
    }),
    TrackableCodeBlock, // Use the patched version
    TrackedChanges.configure({ enabled: true, userId: 'user-123' }),
  ],
})
```

此方法同样适用于 `CodeBlockLowlight` 或任何其他代码块扩展。
