Tiptap 文档并没有真正的页面。Pages 会测量你的内容，并在其上方绘制页眉、页脚和页面间隙，让最终效果看起来像纸张。

有些内容必须先知道页面的位置，才能进行渲染。例如：

- 不得被分页符从中间截断的块
- 只有加载后才能确定高度的嵌入内容
- 必须与页面边缘对齐的覆盖层

布局参与者可以帮助你构建这类内容。你需要向 Pages 提供一个 DOM 元素和一个回调。每次分页更新后，Pages 都会调用该回调。你先进行测量，再调整自己的元素。

内置的 [PageBreak 节点](/pages/core-concepts/page-break-node)和 PagesTableKit 中实验性的[跨分页符行](/pages/guides/row-fragmentation)都使用同一个周期。它们没有特殊权限。你的代码也可以做同样的事。

<Callout title="确认 API 是否可用" variant="hint">
  该 API 位于 `editor.storage.pages` 上。始终使用可选链调用，例如
  `editor.storage.pages?.registerLayoutParticipant?.(…)`。这样一来，你的扩展在没有 Pages
  或使用旧版 Pages 的编辑器中也能正常工作，只是什么也不会执行。
</Callout>

## 布局周期的工作方式

文档发生更改后，Pages 会运行一个布局周期：

1. Pages 按顺序逐一调用每个参与者，顺序为**文档顺序**。文档顶部附近的参与者会先执行。
2. 如果某个参与者报告有变化，Pages 就会重新运行整个周期。这样，文档中靠后的参与者便能测量更新后的位置。
3. 周期会重复，直到没有参与者报告变化。
4. 只有到这时，Pages 才会统计页数并重新绘制页眉和页脚。

文档顺序很重要。顶部附近的块变高时，它下面的所有内容都会下移。因此，文档中靠后的参与者必须在前面的参与者完成后再进行测量。

你在回调中的工作应当简单且严格：进行测量，只更改自己的元素，然后如实说明是否有任何更改。

## API 参考

### registerLayoutParticipant(options)

```ts
const registration = editor.storage.pages?.registerLayoutParticipant?.({
  element: nodeViewDom,
  layout: (context) => {
    // Measure the pages, then adjust your own element.
    return changedSomething
  },
})
```

| 选项      | 含义                                                                                         |
| --------- | -------------------------------------------------------------------------------------------- |
| `element` | 你的根元素。Pages 用它来识别你，并确定你在文档顺序中的位置。                                 |
| `layout`  | 你的回调。Pages 会在每次遍历时调用它，并传入一个 `PageLayoutContext`。                       |

该方法会返回一个包含 `dispose()` 方法的注册对象。在 NodeView 销毁时调用它。重复调用是安全的；它不会移除同一元素更新注册的内容。

### 回调的返回值

| 返回值    | 含义                                                                                                   |
| --------- | ------------------------------------------------------------------------------------------------------ |
| `true`    | “我更改了内容。”Pages 会再遍历一次，让你后面的参与者重新测量。                                        |
| `false`   | “我没有更改任何内容。”                                                                                |
| 无返回值  | Pages 会比较调用前后元素上的内联样式。最好显式返回布尔值。                                             |

在局部遍历中，参见 [requestParticipantLayout](#requestparticipantlayoutelement)：`true` 的含义有所不同，即“请改为运行完整周期”。

### PageLayoutContext

| 字段        | 含义                                                                                                                                                             |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `passToken` | 每次遍历都会生成一个新对象。可将它用作缓存键，这样同一次遍历中的所有参与者便能共享一次开销较大的测量结果。                                                     |
| `defer()`   | 用于说明你的更新会稍后通过 ProseMirror 事务到达。此时 Pages 会延后统计页数。若你直接写入样式，则无需调用此方法。                                                |
| `scope`     | 完整周期中为 `'document'`，局部遍历中为 `'participant'`。旧版 Pages 不会设置此字段。                                                                            |

### requestPageLayout()

当你自己的内容尺寸发生变化、分页需要随之更新时调用。例如图片加载完成、某个区域折叠，或嵌入内容自行调整尺寸时。

该方法会安排在下一帧动画中运行一次完整周期。Pages 会重新测量页眉和页脚，运行已注册的参与者，然后统计页数。同一帧内的多次调用会合并为一个周期。由于周期会测量页眉和页脚，因此在 CSS 更改导致页眉或页脚变高或变矮后，也可以调用此方法。

只有确实发生变化时才调用，不要在每次遍历时都调用。每次运行时都要求开启新周期的参与者会让编辑器一直忙碌，因此 Pages 会停止重复并发出警告。若要在回调中要求再遍历一次，请改为返回 `true`。

### requestParticipantLayout(element)

对于每秒发生多次、且始终局限于**自身元素内部**的变化，这是一种开销更低的选择；这类变化不会使内容变高或变矮，也不会移动页面边缘。拖动交互就是典型例子。

此时 Pages 只会单独运行你的回调，不会遍历文档、统计页数或同步脚注。开销取决于你通知的参与者数量，而非文档大小。

如果回调发现变化比预期更大，请返回 `true` 或抛出异常。Pages 随后会运行完整周期。如果已经安排了完整周期，它会取代任何等待中的局部请求。

## 最简示例

```ts
// In your NodeView constructor:
const registration = editor.storage.pages?.registerLayoutParticipant?.({
  element: dom,
  layout: () => {
    const changed = adjustMyOwnDom(dom)
    return changed
  },
})

// When your own size changes:
editor.storage.pages?.requestPageLayout?.()

// In NodeView.destroy():
registration?.dispose()
```

## 完整示例：不会被分页符截断的块

如果这个提示框原本会跨越分页符，它就会将自身移到下一个分页符之后。对于你自己的节点，这相当于设置 `break-inside: avoid`。

```ts
import { mergeAttributes, Node } from '@tiptap/core'

// Browsers report fractional pixels, so never compare positions with ===.
const PIXEL_TOLERANCE = 0.5

// One measurement per pass, shared by every callout in the document.
const breakRectsPerPass = new WeakMap<object, DOMRect[]>()

function getPageBreakRects(editorDom: HTMLElement, passToken: object): DOMRect[] {
  const cached = breakRectsPerPass.get(passToken)
  if (cached) return cached

  // `.breaker` is the block Pages draws between two pages.
  const rects = Array.from(
    editorDom.querySelectorAll('[data-tiptap-pagination] .breaker'),
    (element) => element.getBoundingClientRect(),
  )
  breakRectsPerPass.set(passToken, rects)
  return rects
}

export const KeepTogetherCallout = Node.create({
  name: 'keepTogetherCallout',
  group: 'block',
  content: 'block+',

  parseHTML() {
    return [{ tag: 'aside[data-keep-together]' }]
  },

  renderHTML({ HTMLAttributes }) {
    return ['aside', mergeAttributes(HTMLAttributes, { 'data-keep-together': '' }), 0]
  },

  addNodeView() {
    return ({ editor }) => {
      const dom = document.createElement('aside')
      dom.setAttribute('data-keep-together', '')

      // How far we push the box down right now. We keep it so we can work out
      // where the box would sit without the push.
      let appliedPush = 0

      const registration = editor.storage.pages?.registerLayoutParticipant?.({
        element: dom,
        layout: (context) => {
          const box = dom.getBoundingClientRect()
          const naturalTop = box.top - appliedPush
          const naturalBottom = naturalTop + box.height

          // Does the box sit across a page break?
          const breaks = getPageBreakRects(editor.view.dom, context.passToken)
          const crossed = breaks.find(
            (rect) => naturalTop < rect.top - PIXEL_TOLERANCE && naturalBottom > rect.top,
          )

          const neededPush = crossed ? crossed.bottom - naturalTop : 0

          // Write only when the value really changed. Writing the same value on
          // every pass looks like a new change every time, and the cycle would
          // never end.
          if (Math.abs(neededPush - appliedPush) <= PIXEL_TOLERANCE) {
            return false
          }

          appliedPush = neededPush
          dom.style.marginTop = neededPush > 0 ? `${neededPush}px` : ''
          return true
        },
      })

      editor.storage.pages?.requestPageLayout?.()

      return {
        dom,
        contentDOM: dom,

        // We change our own style outside of ProseMirror. Without this,
        // ProseMirror treats the DOM as broken, redraws the node, and removes
        // the push again.
        ignoreMutation: (mutation) =>
          mutation.type === 'attributes' &&
          mutation.target === dom &&
          mutation.attributeName === 'style',

        destroy: () => {
          registration?.dispose()
        },
      }
    }
  },
})
```

<Callout title="高度超过一页的块" variant="warning">
  高度超过一页的块无法保持完整。将它移到下一页也无济于事。你的代码必须检测这种情况并且不进行下推，否则就会造成[超大块布局循环](/pages/core-concepts/limitations#oversized-non-splittable-blocks-cause-an-infinite-layout-loop)。Pages 会停止循环并发出警告，但该块的位置仍可能不符合预期。
</Callout>

## 测量页面

在回调中，你通常需要知道页面的位置。有三种方法。

最简单的方法是向 Pages 查询：

```ts
const pages = editor.storage.pages
const position = editor.state.selection.from

const count = pages?.getPageCount?.()
const pageNumber = pages?.getPageForPosition?.(position)
const spaceLeftBelow = pages?.getDistanceToNextPagebreak?.(position)
```

`getDistanceToNextPagebreak(pos)` 和 `getDistanceToPrevPagebreak(pos)` 会返回文档位置到下方或上方页面边缘的像素距离；如果不存在页面边缘，则返回 `null`。它们已经考虑了 `zoom` 选项。

第二种方法是使用 CSS 变量 `--page-max-height`。它表示单页内容区域可能达到的最大高度。

第三种方法是自行测量渲染后的部分：容器 `[data-tiptap-pagination]`、两页之间的块 `.breaker`，以及其中的 `.tiptap-page-header` 和 `.tiptap-page-footer`。如果你需要精确的矩形边界，可以像上面的示例一样使用这种方法。

<Callout title="需要注意的两点" variant="warning">
  Pages 会使用纯色背景绘制页眉和页脚。它们后面的内容会被遮住，而不是绘制在上层。因此，如果参与者的内容会跨越页面边缘，就必须移动该内容或为其留出空间。如果你通过自己的 `--background` 变量设置该背景主题，请改为设置
  `--pages-page-background-color`。

Pages 也支持 `zoom` 选项。你自行测量的矩形使用缩放后的像素值，因此需要除以缩放系数。请从自己的配置中获取该系数。不要尝试通过比较矩形与 `offsetWidth` 来推算。`offsetWidth` 是整数，因此结果会略有偏差；测量位置越靠近文档底部，误差就越大。

</Callout>

## 进阶：通过事务更新

有些参与者会通过 ProseMirror 事务而不是写入样式来应用更新。请在该事务上设置以下一个或两个属性：

- `'pages-layout-participant-change'` 告知 Pages 在更改渲染后再运行一个周期，并在此之前暂缓统计页数。请与创建该事务的遍历中的 `defer()` 一起使用。
- `'pages-layout-participant-scoped-change'` 表示你的更改没有使任何内容上下移动。Pages 因此会跳过额外周期。只有确认该承诺属实时才设置它。错误的承诺会导致页数过时，直到发生下一次实际更改。

[跨分页符的行](/pages/guides/row-fragmentation)就是以这种方式工作的。大多数参与者直接写入样式，因此无需使用它。

## 确保周期正常运行的规则

1. **只操作自己的元素。** 更改其他元素会导致参与者彼此冲突。
2. **仅在值发生变化时写入。** 先使用较小的容差进行比较，因为浏览器会报告小数像素。每次遍历都写入是导致周期无法结束的最常见原因。
3. **如实返回布尔值。** 返回 `true` 会让所有参与者多遍历一次。只有确实更改了内容时才返回它。
4. **使用 `passToken` 缓存。** 无论有多少参与者，每次遍历只测量一次页面。
5. **销毁时释放注册。** Pages 会跳过元素已离开文档的参与者，但释放注册能保持状态整洁。

## 出现问题时

Pages 会保护编辑器，并在浏览器控制台中输出警告。请将以下每种情况都视为回调中的缺陷。

| 发生的情况                                            | Pages 的处理方式                                                                                                                         |
| ----------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| 回调抛出异常                                          | 本次遍历跳过该参与者并继续执行。编辑器仍可正常工作。                                                                                     |
| 回调每次都报告有变化，始终无法稳定                    | 仅暂停该参与者。其他参与者会继续运行。文档发生下一次实际更改后，Pages 会再次调用它。                                                     |
| 每次遍历都请求新周期或局部遍历                        | 停止重复请求。输入文字等实际编辑会清除该状态，因此正常编辑不会触发此情况。                                                               |
| 调用了 `defer()`，但事务始终没有到达                  | 等待一段时间后仍会统计页数，因此页数会继续跟随文档变化。                                                                               |
