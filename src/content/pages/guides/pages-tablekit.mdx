## 哪种配置适合我？

<Callout title="两种场景，一套编辑器扩展" variant="info">
  PagesTableKit 适用于两种场景，它们的区别在于表格内容的来源，而不在于编辑器的接入方式。两种场景使用相同的基础扩展；第二种场景会额外添加 Import 扩展。
</Callout>

- **仅使用 Pages 的工作流。** 您正在构建分页编辑器（适用于打印的版式、信函类文档、报告），需要能够正确分页的表格。内容由用户手动编写。
- **Pages + DOCX 导入工作流。** 您正在导入 `.docx` 文件，并在分页编辑器中呈现。您需要表格既能分页，**又**能忠实保留 DOCX 中设定的格式（声明的宽度、行高、缩进）。

两种场景都使用同一套编辑器扩展：`ConvertKit`（提供 schema）+ `TableKit`（提供适合分页的表格）+ `Pages`（提供布局）。场景 B 还会添加 `ImportDocx`。下文每个部分都会标明适用的场景。

## 安装

```bash
npm i @tiptap-pro/extension-convert-kit \
      @tiptap-pro/extension-pages-tablekit \
      @tiptap-pro/extension-pages
```

场景 B 还需要安装：

```bash
npm i @tiptap-pro/extension-import-docx
```

## 如何设置

PagesTableKit 提供一个 `TableKit` 扩展，其中打包了 Table、TableRow、TableCell 和 TableHeader 扩展。只需注册一次，无需分别接入这四个扩展。

### 场景 A：仅使用 Pages（不导入 DOCX）

注册 `ConvertKit`（禁用其内置的表格扩展）、PagesTableKit 提供的 `TableKit`，以及 `Pages`。

```ts
import { Editor } from '@tiptap/core'
import { ConvertKit } from '@tiptap-pro/extension-convert-kit'
import { TableKit } from '@tiptap-pro/extension-pages-tablekit'
import { Pages } from '@tiptap-pro/extension-pages'

const editor = new Editor({
  extensions: [
    ConvertKit.configure({ table: false }), // disable ConvertKit's tables
    TableKit,
    Pages.configure({
      /* page format, margins, etc. */
    }),
  ],
})
```

ConvertKit 提供文档的节点和标记 schema；PagesTableKit 的 `TableKit` 提供适合分页的表格。ConvertKit 内置的 `ConvertTableKit` **不适合分页**，因此这里要将其禁用。

### 场景 B：Pages + DOCX 导入

在相同的扩展组合上添加 [ImportDocx 扩展](/conversion/import/docx/editor-extension)。ConvertKit 的表格仍保持禁用；PagesTableKit 的 `TableKit` 接受与 ConvertKit 表格相同的 DOCX 单元格属性，因此导入的表格可以正确分页呈现。

```ts
import { Editor } from '@tiptap/core'
import { ConvertKit } from '@tiptap-pro/extension-convert-kit'
import { ImportDocx } from '@tiptap-pro/extension-import-docx'
import { TableKit } from '@tiptap-pro/extension-pages-tablekit'
import { Pages } from '@tiptap-pro/extension-pages'

const editor = new Editor({
  extensions: [
    ConvertKit.configure({ table: false }),
    TableKit,
    ImportDocx.configure({
      /* token, … */
    }),
    Pages.configure({
      /* page format, margins, etc. */
    }),
  ],
})
```

## 支持的功能

### 通用行为（两种场景均适用）

- **适合分页的表格渲染。** 表格位于页面内容区域内，不会发生水平溢出。
- **保留列宽比例。** 当每个单元格都带有 `colwidth` 时，列会按比例缩小以适应页面。无论页面宽度如何，10% / 40% / 50% 的列宽比例都会按 10 / 40 / 50 的比例呈现。
- **行高行为。**
  - `heightRule: "exact"`：行按声明的高度呈现。超出单元格范围的内容和边框会被裁切。
  - `heightRule: "atLeast"`（或未设置）：如果内容或较窄的列原本会导致裁切，行就会纵向增高。
- **合并单元格。** 每个单元格都会保持在自己的列中，合并单元格下方的行也一样。向下合并的单元格会在其覆盖的每一行中保留边框和背景，即使这些样式来自您自己的 CSS 也是如此。请参阅[设置合并单元格的样式](#styling-merged-cells)。
- **极窄列。** 如果列宽小于单元格左右内边距之和，两侧内边距会按相同比例缩小，使单元格及其边框保持在列内。文档和 DOCX 导出仍保留原始内边距。使用 ConvertKit 时，页眉和页脚中的表格会将每个单元格的边距限制为该单元格宽度的四分之一。
- **实时更新。** 添加、删除或重新排序单元格的编辑操作会立即触发行布局更新。

### DOCX 专属行为（场景 B）

如果文档内容由 DOCX 导入器生成，这些附加行为会自动启用，无需单独配置；只要转换器输出了相应属性，PagesTableKit 就会使用它。

- **遵循 DOCX 声明的宽度。** 如果 DOCX 表格的宽度大于页面，表格会按比例缩小到内容区域内，而不会溢出。
- **DOCX 行高。** `w:trHeight` 配合 `w:hRule="exact"` 时会裁切；配合 `w:hRule="atLeast"`（或未设置）时会增高。
- **保留窄间隔列。** DOCX 中 1–15 px 宽的间隔列不会被放大到明显可见的宽度。
- **DOCX 负缩进。** 负的 `w:tblInd` 值（Word 会将其渲染到纸张边距区域）会保留在 `attrs.indent` 中，但视觉上会限制为 0，避免表格超出页面边缘。
- **单元格背景、垂直对齐和各边边框。** 这些样式会直接从 DOCX 导入，无需额外处理。

## 设置合并单元格的样式

在合并单元格首行之后的各行中，合并单元格由 `.tiptap-merged-cell-continuation` 元素绘制。该元素会复制单元格所显示的背景和侧边框，无论这些样式来自单元格属性（例如 DOCX 导入的属性）还是来自您自己的 CSS。它会在单元格所覆盖的最后一行绘制底边框。PagesTableKit 会隐藏合并单元格本身的底边框。

在以下情况下，该元素会重新读取单元格样式：

- 所属表格发生变化。
- 向文档 head 中添加或移除 `<style>` 或 `<link>` 元素、其中 `<style>` 元素的文本发生变化，或其中某个元素的 `href`、`media` 或 `disabled` 属性发生变化。
- 链接的样式表加载完成。
- 编辑器或其任一祖先元素的 `class` 或 `style` 属性发生变化。
- 窗口大小发生变化。
- 文档其他位置的编辑更改了该单元格的背景或边框。PagesTableKit 会在停止输入后检查一次。如果某条规则根据表格外的内容只更改底边框宽度，则要等到表格中发生下一次编辑后才会显示更改。

通过 CSSOM 更改样式表（例如使用 `insertRule` 或 `deleteRule`）不会更改任何元素，也不会触发事件，因此 PagesTableKit 无法检测到这种变化。发生此类更改后，请调用 `refreshTableStyles()`：

```ts
document.styleSheets[0].insertRule('td { border: 2px solid red }')
editor.commands.refreshTableStyles()
```

复制的背景和边框会以内联样式的形式应用到该元素。若要以其他方式设置其样式，请使用以下属性：

- `data-merged-cell` 是合并单元格的节点类型：`tableCell` 或 `tableHeader`。
- 在单元格所覆盖的最后一行中会设置 `data-merged-cell-end`。

## 不支持的功能

<Callout variant="warning" title="这些限制是有意设定的">
  这些不是错误，而是此功能明确记录的边界。如果您的工作流依赖以下任何功能，这个工具就不适合您。
</Callout>

### 通用限制（两种场景均适用）

- **未使用 Pages 扩展的编辑器。** PagesTableKit 是为 Pages 的分页布局设计的；它依赖 Pages 将行限制在页面内。在标准编辑器中，行的呈现会不正确，超宽表格也会发生水平溢出。请改用常规表格扩展。
- **手动编写且 `colwidth` 设置不一致的行。** 只有在**每个**单元格都带有列宽时，才会按比例缩小。在部分单元格带有列宽、部分没有的行中，列的呈现比例可能与预期不同。
- **列宽调整控件。** 支持使用 `@tiptap/extension-table` 提供的拖动调整功能，但最终呈现的宽度可能会按比例缩放，而不是严格等于您拖动设置的像素值；如果每个单元格原本就带有列宽，这种情况尤其明显。
- **较高的合并单元格。** 跨行合并单元格的首行会增高以容纳单元格的全部内容，因此表格可能比在 Word 中更高。

### DOCX 专属限制（场景 B）

- **浮动表格。** 导入器不会转换 DOCX `w:tblpPr`（相对于锚点定位并带有文字环绕的表格）；浮动表格会按普通的堆叠表格呈现。
- **与 Microsoft Word 表格布局完全像素级一致。** Word 使用专有布局算法，综合了固定和按比例调整的尺寸以及内容测量。对于使用 Word“根据内容自动调整”设置创建的表格，请预期会有细微差异。

## 已知问题

### 行必须完整放在同一页

默认情况下，如果表格行无法放入当前页面，就会将整行移到下一页。这与 Microsoft Word 不同，后者会将较高的行拆分到多个页面。

如果行高超过页面内容区域，将其移到下一页也无济于事：它在下一页仍然放不下，编辑器会不断尝试将其向后移动。结果会导致分页无限循环，编辑器无法正常工作。

**如何避免。** 确保行高小于页面内容区域。以下情况尤其需要注意：

- 内容可能无限增长的 `heightRule: "atLeast"` 行。
- 导入的 DOCX 中包含为大于目标页面尺寸的纸张格式设计的超高固定行。
- 单元格内的嵌套表格可能会使外层行高超过页面高度。

若要让较高的行跨页拆分（包括含合并单元格或嵌套表格的行），请启用[行拆分](/pages/guides/row-fragmentation)。

## 使用预期

### 通用（两种场景均适用）

- 表格位于页面内容区域内；固定高度行会裁切，`atLeast` 行会增高。
- 每次事务都会应用更新；添加或删除单元格会立即触发行布局更新。
- 对于非常大的表格（数千行），编辑时可能会明显增加布局开销。如果遇到这种情况，可以考虑手动对大表格分页，或将其拆分到多个文档中。

### DOCX 专属（场景 B）

- 导入时，DOCX 表格会保留其声明的宽度、行高、缩进、背景色和各边边框。
- 超宽 DOCX 表格（常见于 Word 中使用全宽布局的模板）会在视觉上缩小以适应页面，而不会溢出。
- 渲染前无需对导入的 DOCX JSON 进行后处理；这些扩展会读取导入器生成的属性。

## 不要期待

### 通用（两种场景均适用）

- **替代 Pages。** PagesTableKit 只负责表格。分页、页面容器、页眉和页脚仍由 Pages 负责。
- **通过自定义 DOM 代码修改列宽。** 列宽来自 ProseMirror 文档。请通过 `@tiptap/extension-table` 的命令（或您自己的事务）修改，而不要直接写入 `dom.style`。

### DOCX 专属（场景 B）

- **往返转换后完全一致。** 通过 Convert 流程导入再导出 DOCX，无法保证字节级一致。导入时会丢弃不受支持的 DOCX 功能（浮动对象、某些表格样式）。

## 配置参考

PagesTableKit 导出一个 `TableKit` 扩展，其中打包了 Table、TableRow、TableCell 和 TableHeader。

```ts
import { TableKit } from '@tiptap-pro/extension-pages-tablekit'

// Use defaults
TableKit,
```

可以通过 `TableKit.configure()` 配置各个打包的扩展（或使用 `false` 禁用）：

```ts
TableKit.configure({
  table: { cellMinWidth: 1 }, // Table options from @tiptap/extension-table
  tableRow: {
    /* TableRow options */
  },
  tableCell: {
    /* TableCell options */
  },
  tableHeader: false, // disable the header extension entirely
})
```

这些键都会转发给底层扩展的标准选项。

PagesTableKit 还添加了一个自有选项：

```ts
TableKit.configure({
  // Let a tall row continue on the next page instead of moving down whole.
  // Experimental, off by default.
  experimentalRowFragmentation: true,
})
```

请参阅[跨越分页符的行](/pages/guides/row-fragmentation)，了解其作用以及适用的行类型。

它还添加了一个命令：

```ts
editor.commands.refreshTableStyles()
```

在通过 `insertRule` 添加规则等不会导致 DOM 变更的操作之后，`refreshTableStyles()` 会重新读取表格 CSS。合并单元格和单元格内边距随后会采用新样式。该命令不会更改文档，也不会添加撤销步骤。
