import { Callout } from '@/components/ui/Callout'

本指南介绍如何将[旧版身份验证](/authentication/legacy)中记录的按服务分别进行的身份验证，迁移到统一的[身份验证](/authentication)模型。

<Callout title="按自己的节奏迁移" variant="info">
  两种格式可以并行使用。只有 JWT 携带 `aud` 声明时，请求才会路由到新的路径，因此在逐个迁移服务期间，现有集成仍可正常工作。
</Callout>

## 有哪些变化

| 旧版 | 新版 |
| --- | --- |
| 每个服务分别使用一个 App ID 和密钥 | 每个环境使用一对非对称密钥 |
| HS256 共享密钥 | ES256 密钥对（私钥由你保管，Tiptap 存储公钥） |
| REST 请求通过 `X-App-Id` 请求头发送 App ID | 环境 ID 通过 JWT 的 `iss` 声明传递 |
| 每个服务使用不同格式的令牌 | 使用一个包含 `aud` 声明和 `permissions` 数组的令牌 |
| `allowedDocumentNames`、`readonlyDocumentNames`、`commentDocumentNames` | 包含 `action`、`resource` 和可选 `constraints` 的 `permissions` 条目 |

## 第 1 步：创建密钥对

在 Tiptap 控制台中为你的环境创建一对非对称密钥。私钥保存在你的服务器上。Tiptap 只存储公钥，并用它来验证令牌。完整流程请参阅[签署令牌](/authentication#signing-the-token)。

## 第 2 步：用一个令牌替代多个令牌

将按服务分别签署令牌的代码替换为单个令牌：在 `aud` 中列出所需服务，并在 `permissions` 中列出允许执行的操作。[身份验证](/authentication)参考文档介绍了相关声明，并提供了多种语言的签署示例。

## 第 3 步：映射权限

### 协作和文档

文档访问声明将转换为 `permissions` 条目：

| 旧版 | 新版 |
| --- | --- |
| `allowedDocumentNames: ['doc_a']` | `{ "action": "Documents:Write", "resource": "doc_a" }` |
| `readonlyDocumentNames: ['doc_a']` | `{ "action": "Documents:Read", "resource": "doc_a" }` |
| `commentDocumentNames: ['doc_a']` | `{ "action": "Documents:Comment", "resource": "doc_a" }` |
| `allowedDocumentNames: ['team/*']` | `{ "action": "Documents:Write", "resource": "*", "constraints": { "prefix": "team/" } }` |
| 未提供 `allowedDocumentNames`（完全访问权限） | `{ "action": "Documents:Write", "resource": "*" }` |

`Documents:Write` 包含 `Documents:Read` 和 `Documents:Comment` 的权限，因此无需单独列出这两项。

### 转换

将 `aud` 设为 `"Convert"`，并授予集成所使用的格式和方向对应的操作权限。在新的路径中不再读取 `X-App-Id` 请求头，因为环境 ID 通过 `iss` 传递。

```json
{
  "iss": "your-environment-hash-id",
  "aud": "Convert",
  "permissions": [
    { "action": "Convert:Import:Docx", "resource": "*" },
    { "action": "Convert:Export:Pdf", "resource": "*" }
  ]
}
```

### AI 工具包

将 `aud` 设为 `"AI"`，并授予 `AI:Generation`、`AI:Toolkit` 或两者的权限。

```json
{
  "iss": "your-environment-hash-id",
  "aud": "AI",
  "permissions": [
    { "action": "AI:Generation", "resource": "*" },
    { "action": "AI:Toolkit", "resource": "*" }
  ]
}
```

## 前端扩展

`token` 属性在所有地方都保持不变。变化的是令牌的生成方式，以及是否仍需要 App ID：

- **协作。** `TiptapCollabProvider` 仍然同时接收 `appId` 和 `token`，与之前完全相同。
- **转换。** 移除 `appId`。通过同一个 `token` 属性传递新令牌。
- **AI 工具包。** 移除 `appId`。通过同一个 `token` 属性传递新令牌。

所有情况下都继续使用 `token` 属性。你只需更改令牌的签署方式，改用环境密钥对进行签署。

## 第 4 步：逐步部署并停用旧密钥

让两种格式并行运行，直到所有客户端都开始签署符合新模型的令牌。由于 Tiptap 支持每个环境启用多对密钥，因此可以在不中断服务的情况下轮换密钥。流量完全迁移到新模型后，即可停用旧的按服务使用的密钥。
